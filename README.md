# CreditScoreV4 ML Governance

**Production ML Incident Simulation, Remediation & Governance**

CreditScoreV4 ML Governance is a production-style case study built around one continuous ML failure lifecycle. Phase 1 reproduces a vendor-induced model degradation, Phase 2 adds blocking data-quality governance, and Phase 3 demonstrates why contract-valid data still requires statistical drift monitoring.

## Continuous incident story

```text
Healthy Vendor A
  device_risk_score NULL ≈ 3%
        |
        +--> CreditScoreV4 baseline ROC-AUC ≈ 0.80
        |
        +--> Vendor B migration
        |      device_risk_score NULL ≈ 22%
        |              |
        |              +--> same model ROC-AUC ≈ 0.73
        |              +--> Phase 2 quality gate --> BLOCK / quarantine
        |
        +--> Vendor C contract-valid shift
               schema / types / ranges / NULL limits still valid
                        |
                        +--> Phase 2 quality gate --> PASS
                        |
                        +--> feature PSI + KS
                        +--> prediction PSI + KS
                        +--> overall drift --> CRITICAL
```

Measured values are generated by the verification commands; they are not hard-coded production claims.

## Key files

- `configs/phase1.yaml` — deterministic baseline/incident configuration
- `configs/phase2.yaml` — data-quality gate configuration
- `configs/phase3.yaml` — drift scenario, metrics, thresholds, and acceptance gates
- `contracts/credit_application_contract.yaml` — versioned scoring contract
- `src/creditscore/incidents/vendor_migration.py` — Phase 1 Vendor B incident
- `src/creditscore/incidents/vendor_c_drift.py` — Phase 3 contract-valid Vendor C scenario
- `src/creditscore/validation/` — Phase 2 contract/GX blocking controls
- `src/creditscore/drift/psi.py` — reference-binned PSI
- `src/creditscore/drift/ks.py` — two-sample KS statistic/p-value
- `src/creditscore/drift/detector.py` — feature + prediction drift orchestration
- `src/creditscore/drift/report.py` — reference/evidence persistence
- `scripts/verify_phase1.py` — Phase 1 release gate
- `scripts/verify_phase2.py` — Phase 2 release gate
- `scripts/verify_phase3.py` — Phase 3 cumulative release gate

## Scope boundary

Phase 3 detects statistical distribution change. PSI/KS thresholds are configurable project governance controls, not universal regulatory standards. Fairness, explainability, model registry/promotion decisions, serving, observability, and cloud automation remain intentionally deferred to later phases.
