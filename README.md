# CreditScoreV4 ML Governance

**Production ML Incident Simulation, Remediation & Governance**

CreditScoreV4 ML Governance is a production-style case study built around one continuous failure lifecycle. Phase 1 reproduces a schema-compatible vendor migration that degrades the same deployed credit-risk model. Phase 2 adds a blocking data-quality governance gate that uses the exact Phase 1 Vendor B batch as its bad-data fixture.

## Continuous incident story

```text
Healthy Vendor A
  device_risk_score NULL ≈ 3%
        |
        v
CreditScoreV4 baseline ROC-AUC ≈ 0.80
        |
        v
Upstream Vendor B migration
  same schema / numeric range
  device_risk_score NULL ≈ 22%
        |
        v
same deployed model ROC-AUC ≈ 0.73
        |
        +-----------------------------+
        |                             |
        v                             v
Phase 1 incident evidence       Phase 2 data-quality gate
                                      |
                               contract threshold <= 5%
                                      |
                                      v
                                    BLOCK
                                      |
                              quarantine + evidence
```

Measured values are generated by `make phase1-verify`; they are not hard-coded project claims.

## Quick start

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
make phase2-verify
```

A successful Phase 2 release gate should prove that Vendor A passes while the exact Phase 1 Vendor B incident is blocked and quarantined.

## Key files

- `configs/phase1.yaml` — deterministic incident/model configuration
- `configs/phase2.yaml` — quality-gate configuration
- `contracts/credit_application_contract.yaml` — versioned scoring contract
- `src/creditscore/incidents/vendor_migration.py` — Phase 1 incident definition
- `src/creditscore/validation/validator.py` — domain contract validator
- `src/creditscore/validation/gx_engine.py` — Great Expectations adapter
- `src/creditscore/validation/gate.py` — blocking/quarantine decision engine
- `scripts/verify_phase1.py` — Phase 1 release gate
- `scripts/verify_phase2.py` — Phase 2 release gate
- `docs/PHASE1.md` and `docs/PHASE2.md` — phase-specific design notes

## Important scope boundary

Phase 2 is a data-quality control. It does not use PSI/KS to claim distribution drift detection; those controls are intentionally reserved for Phase 3. Fairness metrics are also not part of the production gate until Phase 4.
