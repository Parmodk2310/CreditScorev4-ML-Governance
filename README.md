# CreditScoreV4 ML Governance

**Production ML Incident Simulation, Remediation & Governance**

CreditScoreV4 ML Governance is a production-style case study built around one continuous ML failure lifecycle. Phase 1 reproduces a vendor-induced model degradation, Phase 2 adds blocking data-quality governance, Phase 3 detects contract-valid statistical drift, Phase 4 adds subgroup fairness assessment plus SHAP explainability, and Phase 5 turns that evidence into auditable promotion decisions and registry transitions.

## Continuous incident story

```text
Healthy Vendor A
  device_risk_score NULL ≈ 3%
        |
        +--> CreditScoreV4 baseline ROC-AUC ≈ 0.80
        |
        +--> Vendor B migration
        |      device_risk_score NULL ≈ 22%
        |              |
        |              +--> same model ROC-AUC ≈ 0.73
        |              +--> Phase 2 quality gate --> BLOCK / quarantine
        |
        +--> Vendor C contract-valid shift
               schema / types / ranges / NULL limits still valid
                        |
                        +--> Phase 2 quality gate --> PASS
                        |
                        +--> feature PSI + KS
                        +--> prediction PSI + KS
                        +--> overall drift --> CRITICAL
```


Phase 4 adds a separate Vendor D fixture in which only a synthetic evaluation subgroup receives moderate shifts in non-protected risk proxies. The batch remains contract-valid and aggregate-STABLE under Phase 3, allowing subgroup fairness and SHAP controls to demonstrate a distinct governance failure mode.

Measured values are generated by the verification commands; they are not hard-coded production claims.

## Phase 5 decision matrix

```text
Healthy candidate  quality PASS + drift STABLE + fairness PASS
                  + performance/calibration PASS
                  -> APPROVE -> CANDIDATE -> STAGING

Vendor C candidate quality PASS + drift CRITICAL
                  -> REJECT -> REJECTED

Vendor D candidate quality PASS + aggregate drift STABLE + fairness FAIL
                  -> REJECT -> REJECTED
```

Every decision records policy/gate outcomes, evidence hashes, a deterministic decision ID, registry state, and append-only audit events.

## Quick start

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
make phase5-verify
```

A successful Phase 5 release gate proves that the same policy engine approves a healthy candidate for STAGING while rejecting the Vendor C drift candidate and Vendor D fairness candidate with explicit blocking reasons, evidence hashes, registry state, and an append-only audit trail.

## Scope boundary

Phase 5 makes deterministic synthetic promotion decisions from the evidence produced by earlier controls. Its thresholds are configurable project governance controls, not regulatory rules. Production serving, shadow/canary rollout, runtime observability, rollback automation, workflow orchestration, and cloud deployment remain intentionally deferred to Phases 6–7.
